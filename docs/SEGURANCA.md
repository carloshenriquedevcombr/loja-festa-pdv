# Segurança do sistema e do site

Cada ataque abaixo é **tentado de verdade** pelos testes automáticos (`tests/test_app.py`, parte
"Ataques"). Se alguém mudar o código e abrir uma brecha, o teste falha antes de ir para a loja.

| Ataque | Como o sistema se defende | Teste |
|---|---|---|
| **SQL Injection** | Todo comando ao banco usa parâmetros (`%s`), nunca texto colado. Ordenação e filtros só aceitam valores de uma lista fixa. O app entra no banco com um usuário (`app_user`) que não pode apagar nada nem ver outras lojas. | Aspas, `UNION`, `DROP TABLE`, `pg_sleep` na busca de clientes, peças, pedidos, no site (busca, ordem, data) e no login. Tabelas conferidas depois. |
| **Força bruta** | Conta travada após erros seguidos (5, 10, 15 min…). IP bloqueado por 1 h após 12 erros em 15 min (com aviso no WhatsApp). Limite de pedidos por IP. Senha com Argon2 (lenta de propósito). Cloudflare na frente. | 12 erros → IP bloqueado; outro IP continua entrando; 11º login seguido barrado. |
| **Credential Stuffing** (senhas vazadas de outros sites) | Código no WhatsApp em aparelho novo e sempre para Dona/Dev/Financeiro. Senha de 8 a 32 com os 4 tipos **e** recusa senhas de lista vazada ("Senha@123", "Br@sil2026", "Mudar@123", nome da pessoa ou da loja). Aviso de aparelho/IP novo. | Seis senhas de lista vazada recusadas; código errado recusado. |
| **F12 (vazamento no navegador)** | Cookie da sessão **cifrado** (AES-256-GCM): no F12 → Aplicativo → Cookies aparece só um bloco ilegível. Cookie `HttpOnly` (JavaScript não lê) e `SameSite=Strict`. Sem comentários no HTML, sem script embutido, nada no Console. Documentação da API (`/docs`, `/openapi.json`) desligada. Erros sem detalhe técnico. Servidor não informa nome/versão. Telefone/CPF mascarados para quem não pode ver. Dados de outras pessoas nunca vão para a página. | Cookie decodificado não mostra id/nome/cargo; cookie adulterado não vale; rotas de API 404; varredura dos modelos e do JavaScript. |
| **Command Injection** | O sistema nunca chama o terminal do servidor (nenhum `os.system`, `subprocess`, `eval`). Fotos: o nome enviado é descartado, o arquivo é aberto e regravado pelo Pillow com nome aleatório, sem dados do celular (EXIF). | Varredura do código Python; arquivo PHP com nome `../../etc/passwd;rm -rf .jpg` recusado. |
| **IDOR** (trocar o número na barra de endereço) | Ids são UUID aleatórios. O **banco** (Row Level Security) só devolve dados da loja do sistema, mesmo que o código erre. Página do cliente usa link secreto de 144 bits, não o id. Cada tela confere o cargo antes de mostrar. | Cliente de outra loja pelo id → "não encontrado"; id inventado → 404; id do pedido na página pública não abre. |
| **Escalação de privilégio** | Permissão conferida no servidor em **toda** tela e todo botão (não só escondida). Cargo da Diretoria só a Dona dá; ninguém mexe no próprio cargo. **Botões escondidos**: cada tela só mostra o que o cargo pode usar. | Um robô entra como cada cargo (Atendente, Costureira, Limpeza, Dev, Gerente, Freelance, Dona), clica em **todos** os links e confirma que nenhum leva a "sem permissão". Endereços digitados na mão e formulários forjados → bloqueados. |
| **XSS** | Todo texto é escapado ao montar a página (`<script>` vira texto). CSP bloqueia qualquer script que não seja dos arquivos da loja. Chat mostra mensagens com `textContent`. Links de redes sociais só `https://` do domínio certo. | Nome, observação, busca e chat com `<script>` e `onerror=`; link `javascript:` recusado. |
| **CSRF** | Todo formulário tem token secreto por sessão + cookie `SameSite=Strict`. Até o "Sair" exige o token (outro site não derruba a sessão). | Os 61 formulários do sistema recebem envio sem token → todos recusados, nada gravado. |
| **Broken Authentication** | Argon2; nova sessão a cada entrada (sem fixação); sessão registrada no banco: "Sair" encerra de verdade (o cookie copiado antes para de valer); sai sozinho após 30 min parado e 12 h no total; troca de senha, desativar e "desconectar aparelhos" derrubam todas as sessões; senha fora da regra obriga troca. Mensagem de login igual para usuário inexistente e senha errada. | Cookie copiado antes do "Sair" não entra; sessão parada sai; desconectar derruba; login não revela usuário. |
| **Session Hijacking** | Sessão presa ao **navegador** e ao **aparelho** de quem entrou. Cookie roubado usado em outro navegador/aparelho: a sessão é encerrada para os dois e a Dona e o Dev recebem alerta no WhatsApp. HTTPS obrigatório (HSTS) e cookie `Secure` na VPS. | Cookie copiado para outro navegador e para outro aparelho → recusado, sessão encerrada com motivo, alerta enviado. |
| **Insecure Design** | Regras de dinheiro e reserva no **banco** (não dá para pular pela tela): livro caixa imutável, estorno em vez de apagar, contrato imutável com hash, peça não reserva duas vezes, clique duplo não duplica. Dados pessoais cifrados. Avisos por fila (WhatsApp fora do ar não trava nada). | Testes das travas do banco (`tests/test_banco.py`) e do caixa. |
| **Security Misconfiguration** | Banco em rede interna sem porta aberta; containers só-leitura, sem privilégios (`cap_drop: ALL`, `no-new-privileges`); segredos só no `.env` (fora do git e do Portainer); cabeçalhos CSP, HSTS, X-Frame-Options, nosniff, Referrer-Policy, COOP/CORP, `noindex` no sistema; `no-store` (nada de caixa em cache); área da equipe só do Brasil com Cloudflare; CI roda `bandit` e `pip-audit`. | Cabeçalhos conferidos; Dockerfile conferido. |
| **Business Logic Attacks** (burlar a regra do negócio) | Preço sempre vem do cadastro da peça; o servidor refaz todas as contas no "SIM, GUARDAR" (não confia no formulário); regras de dinheiro, etapas e reserva no **banco** (não dá para pular etapa, retirar sem pagar, cancelar sem ser Dona/Gerente); link de pagamento confere valor com o Mercado Pago; cada formulário grava uma vez só. | Formulário forjado: valor maior que o total, negativo, 99 parcelas, tipo trocado, datas no passado, entrada abaixo do mínimo → recusados. **Corrida**: 5 atendentes reservam a mesma peça no mesmo segundo → só 1 entra. Pular etapa → recusado. |
| **Cabeçalho e protocolo** | Host só da loja (link envenenado em WhatsApp/e-mail); IP real = o que o **proxy** anotou (X-Forwarded-For inventado não engana o bloqueio de IP); CF-Connecting-IP só vale vindo de IP da Cloudflare, e com Cloudflare ligada ninguém entra na área da equipe "pulando" a Cloudflare; só GET/HEAD/POST; dois Content-Length ou Content-Length + chunked (request smuggling) → recusado; redirecionamento só para páginas da loja. | Cada caso acima tentado. |
| **Exposição de dados sensíveis** | CPF/telefone/e-mail/endereço/medidas/contratos cifrados no banco; página da cliente mascarada, `noindex`, sem cache e sem Referer; segredos da URL (link da cliente, aviso do WhatsApp, pagamento) apagados dos logs; nenhuma tela mostra chave/token; senha só como hash Argon2; PDF do contrato sai da fila depois de enviado. | Página pública, telas da Dona, banco e logs conferidos. |
| **DDoS** | Cloudflare (principal), limite de pedidos por IP, envio máximo de 1 MB (fotos 80 MB) mesmo sem Content-Length, consulta travada cortada pelo banco em 15 s, servidor com limite de conexões e contra lentidão proposital (slowloris), avisos em fila (WhatsApp fora do ar não segura o sistema). | 3 MB num formulário → 413; tempo-limite do banco conferido. |
| **Supply chain** (pacote contaminado) | Versões fixas; build **não roda código de instalação** (`--only-binary`); com `requirements.lock` cada pacote precisa bater o **hash**; Actions do GitHub presas por hash de commit; `pip-audit` e `gitleaks` no CI; Dependabot avisa correções; nenhum script de CDN de terceiros (fontes e JS servidos pela loja). | Conferidos Dockerfile, CI e modelos. |
| **Arquivos enviados (logo, fotos)** | Só PNG/JPG/WEBP abertos e regravados pelo sistema (SVG, que pode levar código, é recusado); nome aleatório; só a logo em uso fica pública; o mapa do Google só carrega depois do toque e é o único site de fora permitido em quadro (`frame-src`). | SVG com script e arquivo falso recusados; logo antiga some do ar. |
| **Clickjacking** | `X-Frame-Options: DENY` e `frame-ancestors 'none'` em **todas** as páginas (site, login, página da cliente). | Conferido em 4 páginas. |
| **Deserialization** | Só JSON (nada de pickle/yaml/marshal); cookie cifrado com autenticação (AES-GCM) — objeto forjado nem é aberto; JSON de fora com tamanho e profundidade limitados (bomba de recursão não derruba). | Cookie com pickle; JSON não-objeto; JSON com 3.000 níveis. |
| **Dinheiro a prazo (crediário) e notas** | Crediário só Dona/Gerente/Financeiro liberam (conferido na tela **e** no banco); nunca maior que o saldo; parcela recebida só uma vez e pelo valor exato; nada apagado (cancelar com motivo, estorno reabre). Foto da nota numa pasta separada das fotos do site, nome aleatório, sem EXIF, aberta só por quem mexe no caixa e só se for lançamento da loja. Pix do carnê é texto montado aqui (sem chave de API). Botões escondidos só pela Dona/Dev (trava no banco). | Atendente tentando liberar crediário pelo formulário e direto no banco; clique duplo; parcela paga de novo; nota de outro nome/caminho; costureira abrindo nota. |
| **Conta da cliente e sacola do site** | Sessão da cliente separada da equipe, registrada no banco, presa ao navegador; "Sair" e troca de senha derrubam as sessões. Código do WhatsApp com 5 min e 5 tentativas (hash no cookie cifrado); senha Argon2, trava de 15 min após 5 erros, mesma mensagem para e-mail inexistente. Telefone com ficha só vira conta com o código. Volta depois de entrar só para páginas do site. Preço, entrada, frete e disponibilidade recalculados no servidor ao pagar; um pagamento só vale se bater o valor exato; aviso repetido não lança duas vezes. Usuário "site" do sistema só lança ENTRADA e não entra no sistema. Endereço de entrega cifrado. Nenhum dado de cartão/Pix/boleto passa pelo servidor. | Código errado, cookie copiado, senha fácil, força bruta, redirecionamento para fora, compra de outra conta, valor diferente, aviso repetido, busca por campo de cartão nas telas. |
| **Avaliações, banners e Google** | Link de avaliação assinado (HMAC) — trocar uma letra não abre; uma avaliação por pedido; só depois da devolução/entrega; texto da cliente imutável; só Dona/Gerente aprovam (trava no banco). Banner só com link do próprio site; foto regravada sem EXIF; banner fora do ar tira a foto do ar. Comentários do Google escapados, link do autor só do domínio do Google, chave da API só no servidor. | Token adulterado, `<script>` no comentário, link `javascript:` do Google, atendente aprovando. |
| **Presença online e busca** | Sinal de presença só com token CSRF e da própria origem; guarda só a área da tela (sem ids); não estende a sessão parada; visitante sem conta vira contagem na memória (hash, some em 3 min). "Online agora" e #online só para Dona/Gerente/Dev. Busca do topo respeita o cargo (pedidos, clientes, peças). | Sinal sem token → recusado; id no endereço não é guardado; atendente não vê quem está online nem pelo WhatsApp. |
| **Usuário Master, serviços e Pix/frete (Sprint 8)** | **Master** passa em toda trava do banco e ganha sozinho as permissões novas; só a Dona ou outro Master concede (trava no banco); entra sempre com código no WhatsApp. **Recebi dinheiro sem pedido** só com cliente + serviço cadastrado (trava `entrada_avulsa_com_motivo` no banco). **Link Pix da loja**: código Pix montado aqui, nada lançado até alguém do caixa confirmar que caiu no banco; confirmar duas vezes não lança duas. **Token do Melhor Envio** colado na tela fica cifrado (`pgp_sym_encrypt`), o app não consegue ler a coluna, só a função; nenhuma tela mostra de volta. **Código da parcela do carnê** tem dígito de conferência (número digitado errado não abre outra parcela). | Entrada avulsa direto no banco, Gerente concedendo Master, Limpeza confirmando Pix, clique duplo no Pix, token no HTML/banco, código com um número trocado. |

## O que depende da configuração na VPS

1. `COOKIE_SECURE=1` (já é o padrão no `docker-compose.yml`) e HTTPS pelo Nginx Proxy Manager.
2. Cloudflare na frente com `CLOUDFLARE=1` (docs/VPS.md, passo 6b) e, de preferência, firewall da VPS aceitando 80/443 só dos IPs da Cloudflare.
3. `SITE_URL` preenchido (define o único endereço aceito no cabeçalho Host; outros domínios em `HOSTS_PERMITIDOS`).
4. `bash scripts/travar-dependencias.sh` uma vez (gera `app/requirements.lock` com os hashes) e commit.
5. `.env` com `chmod 600` e `DADOS_CHAVE` guardada fora da VPS.
6. Atualizar o sistema e a VPS (`apt upgrade`) todo mês; aceitar os avisos do Dependabot.

## O que nenhum sistema resolve sozinho

* Celular da loja sem senha de tela ou WhatsApp sem verificação em duas etapas.
* Funcionário que passa a própria senha ou o código do WhatsApp para outra pessoa.
* Computador da loja com vírus que grava o teclado.
